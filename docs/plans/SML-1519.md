# Implementation Plan: SML-1519

## Ticket
**[F-008] `removeAtLine` and `clearFile`/`clearAll` ignore the file's owning workspace folder (multi-root)**

In a multi-root workspace, `removeAtLine` and `runClear` always use `readRegistry(workspaceRoot)` + `getConfiguredDataRoot(workspaceFolders[0])` (where `workspaceRoot` = folder[0]) and resolve relative bookmark URIs against folder[0]. A secondary folder's bookmarks live in that folder's own registry/data, which these commands never read — so "Remove Bookmark", "Clear File", and "Clear All" silently do nothing for files owned by a non-primary folder.

## Scope Classification
Small — 2 files in the extension repo (1 source, 1 test). No core changes, no migrations.

## Overview
Resolve the **owning workspace folder per file** instead of hardcoding `workspaceFolders[0]`. `removeAtLine`/`clearFile` act on the active editor's file → `vscode.workspace.getWorkspaceFolder(editor.document.uri)`. `clearAll` acts on everything → iterate `vscode.workspace.workspaceFolders`, reading each folder's own registry + dataRoot. Mirrors the already-correct `runToggle` (per-file) and `loadAllFolders` (all-folders) patterns. The pure helpers (`bookmarkMatchesActiveFile`, `partitionBookmarksForClear`) and core utils (`workspaceRelativeToUri`, `pathsForDataFile`, `getConfiguredDataRoot`) are already root-parametrized — only the callers change.

## Approach Decision
Generalize `runClear` to take `folders: vscode.WorkspaceFolder[]` and iterate per-folder (each folder's own root + dataRoot, per-(folder,path) delete keying, tag-anchor source URIs resolved with the owning folder's root), keeping a single confirm modal on the **combined** total. `clearFile` passes `[owningFolder]`; `clearAll` passes all `workspaceFolders`. `removeAtLine` swaps its folder[0] bindings for the active file's owning folder, guarding null like `runToggle`. Rejected: looping `runClear` once per folder (would fire the confirm modal per folder and not aggregate totals).
