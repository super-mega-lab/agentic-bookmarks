# SML-1559 — group_moveFile cross-workspace guard

**Severity:** Medium · **Package:** server · **Decision:** reject cross-workspace moves explicitly (product call, approved 2026-06-02).

## Problem

`handleGroupMoveFile` derived `root` from the **source** workspace and resolved/validated
`destFile` against it. Two defects:

1. A `destFile` in a *sibling* registered workspace was false-rejected with the misleading
   `"outside the workspace"` error.
2. A `destFile` in a workspace *nested* under the source root passed the source-root
   containment check, then `moveGroupBetweenFiles(sourceRoot, …)` wrote the group into the
   nested file but updated the **source** registry's nameIndex — a silent nameIndex desync
   (same class as SML-1494).

Root cause: core's `moveGroupBetweenFiles` is single-workspace by construction (one root,
one registry, one nameIndex, one lock domain). Cross-workspace moves are not supported by
the engine; the guard must reject them, not attempt them.

## Fix (server-only)

`packages/server/src/tools/file-group.ts`:
- Add module-local `ownerWorkspace(uri, workspaces)` — returns the **most-specific**
  (longest-matching-root) registered workspace owning `uri`, or `null`. `getWorkspaceForUri`
  returns the *first* array match, which misattributes a nested-workspace file to its
  ancestor; most-specific matching closes the nested-corruption edge regardless of array order.
  Relative URIs match nothing (consistent with `findWorkspaceForUri`) → `null`.
- In `handleGroupMoveFile`: look up source and dest owners; if both resolve to a workspace and
  their roots differ, return a clear `cross-workspace group moves are not supported` error
  before any move. Source-owner drives `root`/`bookmarksDataRoot` (most-specific is also more
  correct than the previous first-match). Existing containment + `s === d` checks unchanged.

`packages/server/src/tools/definitions.ts`:
- Document the same-workspace constraint in the `group_moveFile` tool description (agent-facing).

## Tests (`file-group.test.ts`, `multi-workspace group ops`)

- Sibling-workspace dest → rejected with `/cross-workspace/i`; source still holds the group.
- Nested-workspace dest (outer listed first, the order that defeats first-match) → rejected;
  source registry nameIndex unchanged. This test is RED against a `getWorkspaceForUri`-based
  guard, GREEN with most-specific matching — it justifies `ownerWorkspace`.
- Existing same-workspace move + SML-1522 tag tests + SML-1546 "outside the workspace"
  (unregistered dest) tests remain green (no regression).

## Out of scope

Full cross-workspace move support (two registries/nameIndexes/locks, cross-root anchor
conversion) — a separate feature, not this bug.
