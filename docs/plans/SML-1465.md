# SML-1465: anchor_getFileDiff detects inlined code as a semantic successor

When a setter/getter/method/util function is **inlined** (body substituted at the call site, declaration
deleted), the repair waterfall returned only negative results (`no_match`, trace `deleted`) and the agent
declared it non-repairable — even though the construct's logic still lives at the call site and is already
present in the diff (a deletion referencing the symbol + an addition holding the body).

- **Fix:** add a pure `detectInlinedConstruct(anchor, diff, currentFileLines)` and run it inside
  `handleGetFileDiff` **only when** core's `diagnoseDiff` returns `no_match`. On a hit it replaces the
  diagnosis with `{diagnosis:'inlined', detail:{deletedSymbol, deletedBody, inlinedAt:{line,content,confidence},
  candidates[], explanation}}` pointing the agent at the call site(s). Single call site → `medium`, multiple →
  `low`; no call site → returns null (stays non-repairable). Purely additive — every other diagnosis path
  (including `no_match` without an inline pattern) is byte-for-byte unchanged.
- **Why tool-level in this repo:** the diagnosis enum lives in sibling core's `diagnoseDiff`, but the server
  handler already holds the full net diff (which contains both the deletion and the call-site hunks for the
  same-file case), so detection is a self-contained post-process here — no cross-repo core change. Matches the
  ticket's recommended approach and exact output shape.

Detection is deliberately conservative to avoid misleading the agent: only on `no_match`, the deleted
declaration must tie to the anchor, single-statement bodies only, a generic-body specificity guard, param
renaming tolerated via an identifier-wildcard template, and a required paired symbol-use deletion. Out of
scope (return null): cross-file inlining, multi-commit refactors, multi-statement/complex-transform bodies.
