# SML-1545: anchor_repair reports the resulting anchor kind (range→point collapse)

`handleAnchorRepair` captured the original anchor kind (`const anchorKind = bookmark.anchor.kind`) and echoed
it in the result entry. But a non-smart/non-tag anchor is rebuilt as a **point** (`createAnchor('point', ...)`),
so a repaired **range** bookmark was persisted `kind:'point'` while the response reported `anchorKind:'range'` —
a misreport, with the range end-line silently dropped. An agent trusting the echoed `anchorKind` believed the
bookmark was still a range.

- **Fix:** report the actual resulting kind — `anchorKind: newAnchor.kind` — in the `repaired[]` entry, and add
  `rangeCollapsed: true` when a range anchor was collapsed to a point. Purely additive to the response; smart/
  tag/point repairs report their (unchanged) resulting kind and omit `rangeCollapsed`. The `anchorKind`
  variable is retained for the existing branch logic.
- **Why not preserve the range:** the repair API carries a single `newLine`, so the range end can't be
  reliably reconstructed after the file changed — reporting the true resulting kind is the correct, surgical fix.

Chose option B (report actual kind) over option A (preserve range) from the finding. Breaking risk is LOW: no
code parses the `anchor_repair` response — it's agent-facing (documented in core's `mcp-server.md`/`agentrepair.md`,
which should be updated separately). New `anchor-repair.test.ts` adds the handler's first tests: range→point
collapse (reproduces the bug), point→point (no spurious flag), and smart→smart (kind preserved).
