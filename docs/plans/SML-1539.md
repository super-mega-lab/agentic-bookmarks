# SML-1539 — [F-028] Sticky processes buffered edits from a prior coordinate space

**Scope:** small (1 file modified + 1 new test). **Package:** extension.

## Problem
`packages/extension/src/sticky.ts` debounces `onDidChangeTextDocument` by 150ms, buffering every event's
content changes. It then captures `fileLines` once from the **final** document (`e.document.getText()` of the
last event) and loops over all buffered changes. Per-change `resolvedLine` is shifted by `applyEditDelta` only
*after* each iteration, so on non-final changes the line index and the text snapshot are in different coordinate
spaces. A wrong `lineCache`/line can be persisted to `.bookmarks/shared`, corrupting an anchor.

## Fix
Buffer the per-source-event document text alongside its changes (`{ text, changes }`), capturing
`e.document.getText()` **synchronously in the listener**. In the debounce timeout, process each event's changes
against its own snapshot's `fileLines`; keep batch metrics / lane classification on the final snapshot and keep
`applyEditDelta` cumulative across the batch. The single-event path stays byte-identical to current behavior
(chosen over the more invasive "stop buffering entirely" option). No change to `registerStickyHandler`'s
interface (only consumer: `extension.ts:601`).

## Tests (new `sticky.test.ts` — first test for this file)
`vi.mock('vscode')` + `vi.mock('@agentic-bookmarks/core')` (faithful `updateAnchorLineCache`/`editFileV2`) +
real `./anchorState` + real timers. Cases:
1. 2 edits in one 150ms window → persisted `lineCache` matches the per-event-correct content (buggy code gets a
   line from the wrong snapshot).
2. single in-place edit still refreshes `lineCache` (common path unchanged).
3. multi-event window not touching the anchor line → no write (guards hold).

## Invariants
`registerStickyHandler` signature/return unchanged; all skip guards unchanged; `editFileV2` only on real
mutation; 0-based indices; `stickyGuards.ts` untouched. Baseline before work: 847 tests passing.
