# SML-1575: bookmark_add / group_create / group_delete misroute to ancestor in nested multi-root workspaces

`getWorkspaceForUri` delegates to `findWorkspaceForUri` which returns the **first** array match. When workspace B is nested under workspace A and A appears earlier in the array, URIs inside B are incorrectly attributed to A — `bookmark_add`, `group_create`, and `group_delete` all write into A's registry instead of B's. SML-1559 fixed `group_moveFile` by adding a local `ownerWorkspace()` deepest-match helper, but the three writers were left behind.

- **Fix:** Change `getWorkspaceForUri` in `workspace.ts` to use deepest-match semantics (pick the workspace with the longest matching root path) instead of delegating to the first-match `findWorkspaceForUri`. Remove the now-redundant local `ownerWorkspace` function from `file-group.ts` and replace its two call sites with `getWorkspaceForUri`. This one central change automatically fixes all three writers.
- **Out of scope:** Changes to `findWorkspaceForUri` in core (unnecessary — only one caller exists in the server); fixing read-path operations like `bookmark_list` or `bookmark_search` (they iterate all workspaces, so they're not affected by first-match routing).
- **Tests:** Extend `bookmark.test.ts` (nested-workspace: outer listed first, URI in inner → bookmark lands in inner's registry) and `file-group.test.ts` (group_create and group_delete with same nested setup).
