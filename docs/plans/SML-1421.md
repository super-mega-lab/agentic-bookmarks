# Implementation Plan: SML-1421

## Ticket
**Support drag-and-drop group relocation across files**

Currently, moving a group across files requires right-clicking and using the "Move group to file" context menu with a QuickPick. The ticket adds drag-and-drop as an alternative: dropping a group onto a different RegFileNode in the bookmark tree should move it to that file using the same logic.

## Scope Classification
**Small** — 4 source files + 1 new test file = 5 files

## Overview
The DnD controller's `handleDrop` silently no-ops when `canReorder()` returns false for all dragged items. We add an optional `onFallbackDrop` callback to `DnDOptions` that fires in this case, then wire `FilesGroupsProvider` to handle group→RegFileNode drops by calling `moveGroupBetweenFiles` (already used by `agenticBookmarks.groupMove`). The move-execution logic is extracted from the command into a shared function so both the command and the DnD handler use identical behavior.

## Approach Decision

### Considered Approaches

**Approach A: `onFallbackDrop` callback in `DnDOptions` + `setGroupMoveHandler` on `FilesGroupsProvider` (SELECTED)**
- Adds `onFallbackDrop?: (srcSpecs: DragSpec[], target: vscode.TreeItem) => Promise<void>` to `DnDOptions`
- `FilesGroupsProvider` implements the fallback and provides a `setGroupMoveHandler` method for `extension.ts` to inject the full move deps
- Pros: Follows existing callback DI pattern in `DnDOptions`; generic controller stays generic; testable in isolation; `extension.ts` is the right place for cross-provider orchestration
- Cons: Two layers of indirection (onFallbackDrop → _groupMoveHandler → executeGroupMove); slightly more files touched

**Approach B: Wrap `handleDrop` in `FilesGroupsProvider` constructor**
- Compose the DnD controller returned by `makeDnDController` with a custom `handleDrop` wrapper before storing it as `this.dnd`
- Pros: Doesn't modify generic `dnd-controller.ts`
- Cons: Requires wrapping an internal method; breaks encapsulation; harder to test; duplicates the "parse srcSpecs" logic already in the controller

**Approach C: Execute `agenticBookmarks.groupMove` command programmatically, passing target**
- Modify the existing command to accept an optional target file path argument
- Pros: Minimal new code
- Cons: Commands are public API; mixing drag-drop with command arguments is fragile; command signature change is a breaking change; QuickPick logic entangled with execution logic

### Selection Rationale
Approach A follows the existing pattern exactly — `DnDOptions` already uses callbacks (`onChanged`, `specOf`, `resolveSiblings`). Adding `onFallbackDrop` is a natural extension. The two-layer indirection exists because `FilesGroupsProvider` is constructed without access to `provider.refresh()` and `updateDecorations()` — only `extension.ts` has those. Approach B avoids touching the generic controller but breaks encapsulation. Approach C is fragile.

### Adaptation Guidance
If the `onFallbackDrop` approach proves problematic (e.g., because the fallback fires in unexpected cases), fall back to Approach B: add a `_onGroupFileDrop` private method to `FilesGroupsProvider` and compose the DnD controller's `handleDrop` in the constructor. Non-negotiable constraint: the same `moveGroupBetweenFiles` function must be called in both DnD and context-menu paths.

### Unit 2 — FilesGroupsProvider group-move wiring
**Files:** `packages/extension/src/filesGroupsProvider.ts`
**Test:** existing `filesGroupsProvider.test.ts` (no new tests needed for the wiring layer; behavior tested via unit 1 and integration)
**dependsOn:** [Unit 1]

Changes:
- Add private `_groupMoveHandler?: GroupMoveHandler` property (type defined locally in the file)
- Add `setGroupMoveHandler(handler: GroupMoveHandler): void` method
- In the `makeDnDController` options object, add:
  ```ts
  onFallbackDrop: async (srcSpecs, target) => {
    if (!(target instanceof RegFileNode)) return;
    if (srcSpecs.length !== 1 || srcSpecs[0].kind !== 'group') return;
    if (!this._groupMoveHandler) return;
    const srcSpec = srcSpecs[0];
    const pipeIdx = srcSpec.parentId?.indexOf('|') ?? -1;
    if (pipeIdx < 0) return;
    const srcWsRoot = srcSpec.parentId!.slice(0, pipeIdx);
    const srcFilePath = srcSpec.parentId!.slice(pipeIdx + 1);
    if (target.reg.path === srcFilePath) return;  // same file — canReorder should handle, but guard anyway
    if (target.workspaceRoot !== srcWsRoot) {
      vscode.window.showErrorMessage('Cannot move groups between workspaces.');
      return;
    }
    await this._groupMoveHandler(srcSpec.id, srcFilePath, srcWsRoot, target);
  }
  ```

**Acceptance criteria:**
- AC1: Dragging a group onto a different file node moves it → test via integration; the fallback calls `_groupMoveHandler` with correct args → (verify in code review)
- AC3: Dragging within same file does not trigger cross-file handler → `target.reg.path === srcFilePath` guard returns early

    // Resolve group name for messages (read from file)
    const reg = await readRegistry(wsRoot);
    const dataRoot = getBookmarksDataRoot(reg);

## Risk Assessment & Edge Cases

### Risks
- `parentId` format `wsRoot|dataFilePath` uses `|` as separator. Fragile if paths contain `|`. Pre-existing convention — not introducing new fragility, but noting it.
- Multi-group drag: if the user selects multiple groups and drags them, `srcSpecs.length > 1` — the current plan silently ignores multi-group cross-file drops (only `srcSpecs.length === 1` is handled). This is consistent with the context menu (which operates on a single group). Logged as a future enhancement.
- `readRegistry`/`readFileV2` in the `setGroupMoveHandler` closure in `extension.ts` adds async overhead to the drag-drop handler, but this is acceptable given the drag-drop is already async.

### Edge Cases

| Category | Edge Case | Expected Behavior | Unit |
|----------|-----------|-------------------|------|
| Empty input | `srcSpecs` is empty array | `onFallbackDrop` not called (survivors check fires before) | Unit 1 |
| Null input | `target` is undefined/null in `handleDrop` | Already guarded by existing `if (!target) return;` | Unit 1 |
| Same file | Group dropped on its own file's RegFileNode | `target.reg.path === srcFilePath` guard returns early, no move | Unit 2 |
| Cross-workspace | Group dropped on RegFileNode from different wsRoot | `showErrorMessage` + early return | Unit 2 |
| Multi-select | Multiple groups dragged across files | `srcSpecs.length !== 1` guard, no-op silently | Unit 2 |
| Error path | `moveGroupBetweenFiles` throws | `executeGroupMove` catches, `showErrorMessage` | Unit 3 |
| No handler set | `_groupMoveHandler` not set (e.g., during init race) | `if (!this._groupMoveHandler) return;` guard | Unit 2 |
| Conversion issues | Moved group has bookmarks with anchor conversion issues | `showWarningMessage` with issue count (same as command) | Unit 3 |
| Mixed drag | Non-group items dragged alongside group | `srcSpecs.every(s => s.kind === 'group')` check — actually using `srcSpecs.length === 1 && srcSpecs[0].kind === 'group'` for simplicity | Unit 2 |
| bookmarkFile drag | User drags a RegFileNode onto another RegFileNode | `target instanceof RegFileNode` but `srcSpecs[0].kind === 'bookmarkFile'` — guard returns early | Unit 2 |

## End-to-End Narrative

After implementation, dragging a group across files works as follows:

1. **User starts drag on a GroupNode** (UNCHANGED) → `handleDrag` fires, `specOf` returns `DragSpec{kind:'group', id:groupId, parentId:'wsRoot|dataFilePath'}`, serialized into dataTransfer.

2. **User drops onto a RegFileNode in a different file** (UNCHANGED) → `handleDrop` fires with `target=RegFileNode`.

3. **`canReorder` evaluation** (UNCHANGED) → `specOf(target)` returns `DragSpec{kind:'bookmarkFile'}`, `canReorder(group_spec, file_spec)` returns `false` (different kinds), `survivors=[]`.

4. **`onFallbackDrop` called** (NEW) → `dnd-controller.ts` calls `await opts.onFallbackDrop?.(srcSpecs, target)`.

5. **Group→file validation** (NEW) → Fallback in `FilesGroupsProvider` checks: `target instanceof RegFileNode` ✓, `srcSpec.kind === 'group'` ✓, parses `wsRoot` and `srcFilePath` from `parentId`, checks same-workspace ✓.

6. **`_groupMoveHandler` called** (NEW) → `FilesGroupsProvider` delegates to the handler set by `extension.ts`.

7. **Group name resolved, `executeGroupMove` called** (NEW) → `extension.ts` closure reads the file to get the group name, calls `executeGroupMove(deps, groupId, groupName, srcFilePath, dstFilePath, wsRoot)`.

8. **`moveGroupBetweenFiles` executes** (UNCHANGED logic, now in shared function) → core function moves the group, returns `MoveResult`.

9. **Messages shown** (UNCHANGED) → conversion issues shown if any; success message otherwise.

10. **Tag insertions/removals handled** (UNCHANGED) → same tag comment logic as the context menu command.

11. **Trees refresh** (UNCHANGED) → `provider.refresh()`, `filesGroups.refresh()`, `updateDecorations()`.

Steps 1-3 and 8-11 are either unchanged or use identical code. Steps 4-7 are new. AC1 satisfied by step 5-8. AC2 satisfied by step 6-11 (same `executeGroupMove` as the context menu). AC3 satisfied by same-file guard in step 5.
