# SML-1544: anchor_validate summary classification parity with classifyAnchorStatus

`handleAnchorValidate` computed its `summary` (`valid`/`warning`/`broken`) with hardcoded thresholds —
`valid = resolved && (!score || score>=0.85)`, `warning = resolved && score<0.85`, `broken = !resolved` —
instead of the core `classifyAnchorStatus`. That diverged from the product on two axes: (1) an unresolved
anchor with `lineCacheOnly:true` is a `warning` (deep-flex pending), not `broken`; (2) a resolved low-score
**shared** (non-local) bookmark is suppressed to `valid` unless `showWarningOnShared`. `anchor_validate` never
read `showWarningOnShared`, so its broken/warning counts contradicted `anchor_listBroken` and the extension UI.
The sibling `handleAnchorListBroken` already classifies via `classifyAnchorStatus` for this exact parity
(SML-1503/1508).

- Add `classifyAnchorStatus` to the core import; read `showWarningOnShared` from `anchorSettings` (?? false)
  next to the existing `enableFlexContext`/`enableFlexContextShared`.
- Compute `status = classifyAnchorStatus(r, { isLocal, showWarningOnShared })` per **raw** resolution result,
  add `status` to each per-result entry (the tool already advertises "validation status for each anchor"; the
  field is additive — smoke consumers read only `.line`), and derive the `summary` counts from `status`. The
  magic `0.85` is gone — it now lives in the classifier as `SMART_ANCHOR_HIGH_CONFIDENCE`.
- **Resolution is unchanged** — the ticket states per-result `resolved`/`score` remain accurate; only the
  summary classification was wrong.

Covered by new `tools/anchor-repair.test.ts`: clean→valid and fully-broken→broken positive controls,
unresolved+lineCacheOnly→warning (divergence #1, reusing the core lineCacheOnly recipe), resolved low-score
shared→valid-suppressed by default and →warning under `showWarningOnShared:true` (divergence #2, reusing the
SML-1508 flex-only shared-anchor fixture).
